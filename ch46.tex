\section{使用共享内存优化矩阵乘法：分块技术}

\subsection{引言：全局内存的重复读取问题}

考察矩阵乘法 $C = A \times B$，其中 $A$、$B$、$C$ 均为方阵。为了计算矩阵 $C$ 中的全部元素，矩阵 $A$ 的第一行需要从全局内存中读取多少次？

回顾矩阵乘法的计算规则：计算 $C_{1,1}$ 需要将 $A$ 的第一行与 $B$ 的第一列做内积；计算 $C_{1,2}$ 需要将 $A$ 的第一行与 $B$ 的第二列做内积；计算 $C_{1,3}$ 需要将 $A$ 的第一行与 $B$ 的第三列做内积。因此，若 $B$ 有三列，则 $A$ 的第一行需要被读取三次。推广到一般情形：若 $B$ 有 100 列，则 $A$ 的第一行需要被读取 100 次。

同一行数据被反复从全局内存加载，构成了矩阵乘法中最典型的性能瓶颈之一。

\subsection{全局内存与共享内存的延迟对比}

根据第一部分硬件章节中引用的研究数据，各层级存储器的访问延迟大致如下：

\begin{center}
\begin{tabular}{|l|c|}
\hline
\textbf{存储器类型} & \textbf{访问延迟（时钟周期）} \\
\hline
全局内存（Global Memory） & 约 300（浮动 $\pm$10--20） \\
\hline
共享内存（Shared Memory） & 约 20--22 \\
\hline
\end{tabular}
\end{center}

共享内存的读写延迟比全局内存低一个数量级。当矩阵的某一列包含 $K$ 个元素时，同一行数据将被重复读取 $K$ 次；若数据始终驻留于全局内存，则每次访问均须承担约 300 个周期的延迟，成为整个应用的性能瓶颈。

\subsection{L1 缓存与共享内存的本质差异}

一个自然的问题是：数据从全局内存被加载后，通常会经由 L2、L1 缓存驻留在 SM 附近，L1 缓存的延迟同样较低，为何仍需要使用共享内存？

关键在于\textbf{数据驻留的确定性}。L1 缓存由硬件管理，程序员无法控制其换入换出策略。当多个线程块竞争同一 SM 的 L1 容量时，硬件可能随时驱逐其中的数据。若矩阵 $A$ 的第一行被逐出 L1，后续访问将被迫再次从全局内存加载，重复承担高延迟开销。

共享内存则不同，它属于\textbf{软件控制的内存}：数据的加载与驻留完全由程序显式管理。只要程序员不主动覆盖，数据在整个内核执行期间都保证驻留在共享内存中。因此，对于需要多次重用的数据，使用共享内存可以在\textbf{确定性}的前提下获得低延迟访问。

综上所述，本应用的瓶颈在于：同一行数据被多次从高延迟的全局内存读取；解决方案是将需要重用的数据显式加载到共享内存中，该优化技术称为\textbf{分块（Tiling）}。

\subsection{分块与瓦片的基本概念}

\subsubsection{瓦片的定义}

在矩阵乘法中，矩阵 $C$ 的每个元素都依赖于 $A$ 的\textbf{一整行}与 $B$ 的\textbf{一整列}（区别于向量加法中一个元素对应一个元素）。因此，GPU 并行化的基本策略是：将矩阵 $C$ 划分为若干子区域，每个子区域称为一个\textbf{瓦片（Tile）}，并将每个瓦片分配给一个线程块独立计算。

瓦片大小与瓦片数量是两个不同的概念：例如一个 $3 \times 3$ 的矩阵可划分为 9 个瓦片（瓦片大小为 1）；而在实际应用中，通常将 $C$ 划分为大小为 $16 \times 16$ 的瓦片。瓦片大小的选取受两个因素约束：

\begin{itemize}
    \item \textbf{共享内存容量}：瓦片对应的 $A$ 行片段与 $B$ 列片段必须能够放入共享内存。
    \item \textbf{线程数上限}：每个瓦片由 $TILE\_SIZE \times TILE\_SIZE$ 个线程计算，不能超过每个块的线程数上限（1024）。
\end{itemize}

\subsubsection{网格与线程块配置}

以 $N = 512$、$TILE\_SIZE = 16$ 为例：

\begin{itemize}
    \item \textbf{块大小（Block Size）}：$16 \times 16 = 256$ 个线程，即 X、Y 维度的线程 ID 均从 0 到 15。
    \item \textbf{网格大小（Grid Size）}：X、Y 维度的块数量均为
    \[
    \frac{N + TILE\_SIZE - 1}{TILE\_SIZE} = \frac{512 + 16 - 1}{16} = 32
    \]
    即网格为 $32 \times 32$ 个线程块。
    \item \textbf{总线程数}：$32 \times 32$ 块 $\times$ 256 线程/块 $= 262144 = 512 \times 512$，恰好等于矩阵 $C$ 的元素数，与向量加法中"线程数等于元素数"的原则一致。
\end{itemize}

\subsubsection{K 维循环累加}

单个瓦片（$16 \times 16$ 区域）的计算需要 $A$ 中对应的 16 个整行与 $B$ 中对应的 16 个整列，每行/列包含 512 个元素。将其按 16 个元素一段划分为 32 个片段（块），则瓦片的计算结果为：

\[
C_{tile} = \sum_{t=0}^{31} A_{tile,t} \times B_{t,tile}
\]

其中 $t$ 为片段索引（K 维迭代变量）。以第一个瓦片（块索引 $(0,0)$）为例：

\begin{itemize}
    \item $t=0$：$A$ 的第 0--15 列片段与 $B$ 的第 0--15 行片段相乘，结果累加到 sum；
    \item $t=1$：$A$ 的第 16--31 列片段与 $B$ 的第 16--31 行片段相乘，继续累加；
    \item 依此类推，直至 $t=31$，完成全部 512 个元素的乘加运算。
\end{itemize}

注意 K 维步长：对 $A$ 而言，相邻片段在 X 维度偏移 16；对 $B$ 而言，相邻片段在 Y 维度偏移 16（对应 X 维度偏移 $16 \times 512$）。因此，需要两层循环：外层遍历 K 维片段（$t$），内层遍历片段内的 16 个元素（$k$）。

\subsection{共享内存实现}

\subsubsection{共享内存数组的声明}

在 CUDA 内核中，共享内存变量使用 \texttt{\_\_shared\_\_} 关键字声明。矩阵 $A$、$B$ 的元素类型为 float，因此声明两个 $TILE\_SIZE \times TILE\_SIZE$ 的二维数组：

\begin{lstlisting}
__shared__ float s_a[TILE_SIZE][TILE_SIZE];
__shared__ float s_b[TILE_SIZE][TILE_SIZE];
\end{lstlisting}

\subsubsection{共享内存容量核算}

以 $TILE\_SIZE = 16$ 为例，共享内存占用为：

\[
16 \times 16 \times 4\ \text{字节} \times 2\ \text{个数组} / 1024 = 2\ \text{KB}
\]

该值远小于各架构的共享内存上限（如 RTX 3060 约 96--100 KB，A100 可达 160 KB）。调整 $TILE\_SIZE$ 时须重新核算，确保不超过硬件容量。

\subsubsection{数据加载与索引计算}

在加载共享内存之前，$A$、$B$ 的数据驻留于全局内存（由 \texttt{cudaMemcpy} 从主机复制而来）。每个线程将全局内存中的一个元素复制到共享内存的对应位置。

\begin{itemize}
    \item \textbf{行索引与列索引}：
    \begin{lstlisting}
int row = blockIdx.y * TILE_SIZE + threadIdx.y;
int col = blockIdx.x * TILE_SIZE + threadIdx.x;
    \end{lstlisting}
    行索引使用 Y 维度（块的 Y 索引与线程的 Y ID），列索引使用 X 维度。

    \item \textbf{加载 $A$ 的片段}：
    \begin{lstlisting}
s_a[threadIdx.y][threadIdx.x] = a[row * N + t * TILE_SIZE + threadIdx.x];
    \end{lstlisting}
    其中 \texttt{row * N} 定位到矩阵 $A$ 的第 row 行（每行 N 个元素）；\texttt{t * TILE\_SIZE} 定位到 K 维第 $t$ 个片段在行内的起始列；\texttt{threadIdx.x} 为片段内偏移（0--15）。

    \item \textbf{加载 $B$ 的片段}：
    \begin{lstlisting}
s_b[threadIdx.y][threadIdx.x] = b[(t * TILE_SIZE + threadIdx.y) * N + col];
    \end{lstlisting}
    $B$ 的片段沿 Y 维度推进：\texttt{t * TILE\_SIZE + threadIdx.y} 给出片段起始行加行内偏移，乘以 N 后加上列索引 col 完成定位。
\end{itemize}

\subsubsection{同步与计算}

\begin{itemize}
    \item \textbf{第一次同步}：加载 $A$、$B$ 的当前片段后，必须调用 \texttt{\_\_syncthreads()}，确保块内所有线程完成加载后才能开始计算，否则部分线程可能读取到尚未写入的共享内存数据。
    \item \textbf{片段内乘加}：对片段内的 16 个元素执行乘加运算：
    \begin{lstlisting}
for (int k = 0; k < TILE_SIZE; k++) {
    sum += s_a[threadIdx.y][k] * s_b[k][threadIdx.x];
}
    \end{lstlisting}
    \item \textbf{第二次同步}：在进入下一个片段的加载之前再次调用 \texttt{\_\_syncthreads()}，防止某些线程在其余线程完成计算前覆盖共享内存。
\end{itemize}

全部片段累加完毕后，将结果写回全局内存：

\begin{lstlisting}
c[row * N + col] = sum;
\end{lstlisting}

\subsubsection{完整内核代码}

\begin{lstlisting}
__global__ void matmul_tiled(float* a, float* b, float* c, int n) {
    __shared__ float s_a[TILE_SIZE][TILE_SIZE];
    __shared__ float s_b[TILE_SIZE][TILE_SIZE];

    int row = blockIdx.y * TILE_SIZE + threadIdx.y;
    int col = blockIdx.x * TILE_SIZE + threadIdx.x;

    float sum = 0.0f;
    int numTiles = N / TILE_SIZE;

    for (int t = 0; t < numTiles; t++) {
        // 将 A、B 的第 t 个片段从全局内存加载到共享内存
        s_a[threadIdx.y][threadIdx.x] = a[row * N + t * TILE_SIZE + threadIdx.x];
        s_b[threadIdx.y][threadIdx.x] = b[(t * TILE_SIZE + threadIdx.y) * N + col];

        __syncthreads();

        // 对当前片段执行乘加运算
        for (int k = 0; k < TILE_SIZE; k++) {
            sum += s_a[threadIdx.y][k] * s_b[k][threadIdx.x];
        }

        __syncthreads();
    }

    c[row * N + col] = sum;
}
\end{lstlisting}

\subsection{常见错误与调试}

在实现过程中容易出现的错误包括：

\begin{enumerate}
    \item \textbf{语法错误}：语句末尾缺少分号、变量（如 \texttt{numTiles}）未声明、常量名大小写不一致（如 \texttt{TILE\_SIZE} 误写为 \texttt{tile\_size}）等。
    \item \textbf{逻辑错误（关键）}：将片段乘加循环（内层 for 循环）错误地放在片段遍历循环（外层 for 循环）之外。此时程序会先加载完所有片段，再仅对\textbf{最后一个片段}执行乘加，计算结果严重错误。正确的控制流应当是：\textbf{加载一个片段 $\to$ 同步 $\to$ 乘加累加 $\to$ 同步}，如此循环往复，直至遍历完 K 维的所有片段。
\end{enumerate}

\subsection{性能评估}

\subsubsection{与朴素实现的对比}

在 $N = 512$ 时，使用 Nsight Compute 命令行工具测得：

\begin{center}
\begin{tabular}{|l|c|c|}
\hline
\textbf{实现} & \textbf{执行时间（N=512）} & \textbf{执行时间（N=1024）} \\
\hline
朴素矩阵乘法（全局内存） & 360 微秒 & 约 3 毫秒 \\
\hline
分块矩阵乘法（共享内存） & 约 251 微秒 & 约 2 毫秒 \\
\hline
\end{tabular}
\end{center}

使用共享内存后，执行时间由 360 微秒降至约 251 微秒，性能提升约 30\%--40\%。当矩阵规模增大至 $N = 1024$ 时，同样取得约 33\% 的提升，说明共享内存优化在较大规模下依然有效。

\subsubsection{瓦片大小的选择}

进一步调整 $TILE\_SIZE$ 观察其影响：

\begin{center}
\begin{tabular}{|l|c|c|c|}
\hline
\textbf{TILE\_SIZE} & \textbf{每块线程数} & \textbf{共享内存占用} & \textbf{结果（N=1024）} \\
\hline
16 & 256 & 2 KB & 约 2 毫秒（最优） \\
\hline
32 & 1024 & 8 KB & 约 2.1 毫秒（略有下降） \\
\hline
64 & 4096 & 32 KB & 内核无法执行 \\
\hline
\end{tabular}
\end{center}

\begin{itemize}
    \item $TILE\_SIZE = 32$ 时，每块线程数为 1024，已达硬件规定的每块线程数上限。由于线程规模过大、占用率受限，执行时间反而略有增加。
    \item $TILE\_SIZE = 64$ 时，每块线程数为 $64 \times 64 = 4096$，超过 1024 的上限，内核无法启动（Nsight Compute 提示 "No kernels were profiled"）。注意：此限制源于线程数上限，而非共享内存容量（64 瓦片仅需 32 KB，未超出硬件共享内存上限）。
\end{itemize}

\subsection{总结}

本节通过分块技术将矩阵乘法中被反复读取的行/列数据显式加载到共享内存，将每元素访问延迟从约 300 个周期降至约 20 个周期，在 $N = 512$ 与 $N = 1024$ 规模下均获得约 30\%--40\% 的性能提升。要点如下：

\begin{enumerate}
    \item 矩阵乘法的数据重用特性（同一行/列被读取 $K$ 次）使其天然适合共享内存优化。
    \item 共享内存属于软件控制的内存，数据驻留具有确定性，这是 L1 缓存无法保证的。
    \item 瓦片大小的选取须同时满足共享内存容量与每块线程数上限（1024）两个约束。
    \item 分块实现的控制流必须严格遵循"加载 $\to$ 同步 $\to$ 计算 $\to$ 同步"的顺序，任何一环缺失都将导致错误结果。
\end{enumerate}
