\section{CUDA GPU 并行编程：向量归约优化}

本节讲解向量归约（Vector Reduction）应用的第一项优化。

\subsection{使用 while 循环自动化多步归约}

在前面的讨论中提到，需要反复调用 GPU kernel，直到某一步中的 block 数量小于 block size，此时进入最后一步（仅需一个 block）。基于此逻辑，可设置 while 循环：若 grid size 大于 1，则继续迭代执行 kernel；若 grid size 等于 1，则执行最后一步即可。

当 grid size 大于 1 时，使用新的计算逻辑执行 kernel。例如，第一步的 grid size 为 4096，该值存储在变量 N 中，意味着第一步之后 N 等于 4096。下一步的新 grid size 计算公式为：

\[
\text{new\_grid\_size} = (N + \text{block\_size} - 1) / \text{block\_size}
\]

代入数值：$(4096 + 256 - 1) / 256 = 16$，与之前的手动计算一致。while 循环检查 grid size 是否大于 1，当前为 16，因此继续执行 kernel。此时 N 从 $1024 \times 1024$ 变为 4096，block size 保持不变，grid size 为 16。

完成第二步后，N 变为 16。代入公式：$(16 + 256 - 1) / 256 = 1$。因为仅 16 个元素不足一个完整 block（256 线程），但最少需要一个 block，所以 grid size 等于 1。while 循环再次检查：grid size 等于 1，不满足大于 1 的条件，因此跳出循环，执行最后一步函数。最后一步中 grid size 为 1，N 为 16。

整个流程经历了 4096 $\to$ 16 $\to$ 1 三个阶段，与之前手动配置多次 kernel 的结果一致。编译并运行程序，对比 GPU 和 CPU 的输出结果，确认 while 循环工作正确。

\subsection{移除取模过滤器的优化}

接下来讨论内核代码中的过滤器（filter）。该过滤器的作用是筛选出每一步中实际需要工作的线程：第一步需要偶数编号线程（0, 2, 4, ..., 14），第二步需要线程 0, 4, 8, 12，第三步需要 0 和 8，最后一步仅需线程 0。

\subsubsection{移除过滤器的可行性分析}

如果移除过滤器，所有线程都会执行加法指令。以线程 1 为例，它会将索引 1 和索引 2 的值相加，并将结果存入索引 1。在第一步中，索引 1 处的值从 1 变为 9（即 $1+8$ 或其他值，取决于具体数据）。

关键问题在于：后续步骤是否会使用索引 1 处的值？答案是否定的。由于步长（stride）机制的存在，第二步的步长为 2，操作变为 \texttt{index = 0 + 2}，而非加 1。因此完全不会访问索引 1 的元素。其他所有步骤同理。

由此可见，移除过滤器不会影响最终输出，因为被"多余"线程写入的值在后续步骤中根本不会被读取。

\subsubsection{取模运算的性能开销}

移除过滤器的根本原因在于取模运算（modulus operation）在 GPU 上的开销极高。根据 NVIDIA GPU 指令延迟的研究数据：

\begin{itemize}
    \item 加法运算：约 2--4 个时钟周期
    \item 乘法运算：约 2--9 个时钟周期
    \item 除法/取模运算：约 290 个时钟周期
\end{itemize}

取模运算的开销是加法的近 100 倍。除非在特定场景下不可替代，否则应尽量避免使用除法和取模运算，并以开销更小的操作替代。

\subsubsection{性能对比验证}

编译带过滤器的基准版本（报告 A），然后移除过滤器重新编译（报告 B）。在 Nsight Compute 中以 A 为基准线，对比 B 版本的性能。

结果显示：不带过滤器版本的执行时间为 176 微秒，而基准版本为 283 微秒，性能提升近 40\%。第二和第三个 kernel 的性能提升接近 100\%。（指标显示负值是因为衡量的是"持续时间"，时间越短性能越好。）

运行程序验证 CPU 和 GPU 的输出一致性，确认移除过滤器后程序依然产生正确的归约结果。

\subsection{汇编级分析}

在 Nsight Compute 的源码视图中观察汇编代码，可以更深入地理解性能差异的原因。

\textbf{不带过滤器的版本：} 函数的 if 语句仅包含约 6 条汇编指令，结构非常精简。尽管如此，该 if 语句仍然导致了约 60\% 的流水线停顿（stalling）。其中的全局内存加载（load）操作单独造成了约 9\% 的停顿。

\textbf{带过滤器的版本：} 相同的加载操作位于源码第 131 行（不带过滤器版本在第 66 行），说明在此之前增加了大量额外指令。这些额外指令全部来自取模运算所产生的 if 条件判断，包含五六十条指令——分支跳转、条件移动、同步操作等。相比之下，不带过滤器版本的同一个 if 语句仅有 6 条指令。

这正是执行时间从 283 微秒优化到 176 微秒的根本原因：取模运算消耗了过多的时钟周期，导致汇编代码膨胀。

\subsection{调试器验证}

通过 Visual Studio 的 CUDA 调试功能，可以直观地验证有无过滤器时的行为差异。

\textbf{带过滤器的情况：} 在内存视图中观察 input 向量，单步执行完第一个 warp（前 32 个线程）后，可以看到：第 1 个元素被修改，第 2 个未变，第 3 个被修改，第 4 个未变……交替进行。这验证了过滤器的作用——仅特定位置的元素被更新。

\textbf{不带过滤器的情况：} 移除过滤器后重新调试，执行第一个 warp 后可以观察到：所有元素均被修改——第 1 个、第 2 个、第 3 个、第 4 个……全部被更新。这印证了理论分析：移除过滤器后所有线程都参与了计算，但如前所述，"多余"的写入不会影响最终结果。

本节介绍了向量归约的第一项重要优化——通过移除取模过滤器减少指令数量，从而将第一个 kernel 的执行时间从 283 微秒降至 176 微秒。后续章节将探讨更多优化技术。
