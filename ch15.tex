\section{NVIDIA GPU 硬件与软件层级结构及 CUDA 介绍}

大家好，在今天的文章中，我们将深入探讨 NVIDIA GPU 的硬件与软件层级结构，并介绍 CUDA。让我们从 CUDA
的介绍开始。CUDA 全称为 Compute Unified DeviceArchitecture（统一计算设备架构），
是由 NVIDIA开发的一个并行计算平台和应用程序编程接口（API）。CUDA 允许软件开发者使用 NVIDIA的图形处
理单元进行通用目的计算，这种方法被称为 GPGPU（General-Purpose computing onGraphics Processing Units，即图形处理单元上的通用计算）。


在本节开头，我想强调三个关键点。第一，CUDA 基于 C 编程语言，这是一个优势，因为它让熟悉 C语言的开发者能够轻松编
写可在 NVIDIA GPU 上执行的软件。第二个关键点是 CUDA 编译器。该编译器名为\texttt{nvcc}，它
不仅仅是一个普通的编译器，而是 CUDA 工具包的核心。\texttt{nvcc}的作用远不止将 CUDA代码转换为可执
行文件或机器码，它在开发过程中扮演着多重关键角色。随着本课程的推进，我们将逐步揭示\texttt{nvcc} 命令的多功
能性，以及它如何优化我们的 CUDA 应用程序。

我们需要讨论的第三点是主机（Host）与设备（Device）这两个术语的区别。这是为了确保我们能充分利用 GPU的资源。
通常，主机指的是 CPU 及其关联的全局内存（即 RAM），而设备则指 GPU及其全局内存。这种区分不仅在术语上非常重要
，在我们编写软件的方式上也至关重要，它影响代码结构、数据传输和内存管理。本图中左侧部分代表主机，右侧部分代表设备（即GPU）。

\subsection{硬件四级层级}

让我们回顾并深入探讨 GPU 硬件架构层级与其软件部分之间的关系。它包含四个明确的硬件组织层级。如前所述，GPU的结构是
分层的：最顶层是 GPU 本身，GPU 封装了所有单元；每个 SM（StreamingMultiprocessor，流式
多处理器）构成该层级结构的第二级。这一设计已在 Volta 白皮书文章中详细说明。在该GPU 内部，包含大量流式多处理器
。请务必观看 Volta 白皮书文章，因为它非常重要。

接着，每个流式多处理器又被进一步划分为若干个分区（Sub-partition / ProcessingBlock），构成
硬件结构的第三级。在我们的示例中，即 Volta 和 Ampere 架构中，每个 SM包含四个这样的分区。如你在这张来自
Volta 白皮书的图中所见，SM 被划分为四个分区。如果你查阅 Ampere白皮书也能看到类似的结构。

在第四级，也就是最细粒度的层级，我们在每个分区内找到独立的计算单元。这类单元的一个例子是浮点核心（即 FP32核心），它
负责执行浮点运算。总结来说，这些核心是 GPU 内部处理计算的基本单元。

综上所述，GPU 的硬件架构可视为一个四级层级结构：从整个 GPU开始逐级向下，经过流式多处理器（SM），再到其内部的分
区作为第三级，最终到达各个独立的计算核心。这些不同的硬件层级反过来要求对应的软件应用程序具备相似的结构，这一点非常重要。

例如，假设我们有一个 CUDA 应用程序，如图所示，用这个方框表示。该应用程序设计用于在整个 GPU上运行。但这里的问题

\subsection{软件层级：块与GigaThread Engine}

编写 CUDA 代码的第一步是将该应用程序中的 GPU核函数（Kernel）划分成更小的软件单元，称为块（Block）或
线程块（Thread Block）。在所有 CUDA应用程序中，第一步是首先配置每个核函数的块数量。如果我们将这个方框整
体视为一个 CUDA应用程序，那么就可以应用这一原则：我们可以将它划分为更小的块。如图所示，这些小方框中的每一个都被称为
一个块或线程块，这两个名称都是正确的。这种在应用程序中的分段或划分对应了GPU 的前两个硬件层级——整个应用程序设计用于
在整个 GPU 上执行。

然而这引发了一个问题：软件中的第二级是指不同的块在不同的 SM上执行。在左侧，我们有由这些软件块（线程块）表示的任务；在
另一侧，我们有可视为“工人”的SM。左边是由块表示的任务或作业，右边是由 SM表示的工人。这里的管理者是谁？谁负责将这些
软件任务、这些作业分配给工人（SM）？

要回答这个问题，我们需要了解另一个单元，称为 GigaThread Engine。GigaThread Engine 是
GPU 内部最重要的单元之一，它的关键功能之一就是高效地将这些软件块（任务/作业）分配到各个 SM上。为了进一步澄清这一
概念，我更倾向于打开 Volta白皮书。持续查阅白皮书非常重要，因为它能提供更多信息。如果我们参考 Volta 白皮书来
查看 GigaThreadEngine 的位置，如这张图所示，GigaThread Engine 位于整个 GPU的整体
结构之中。它连接到所有流式多处理器（SM）。请记住，它负责为这些 SM 提供必要的软件块或软件任务。

将同样的原理应用到下一层级。假设有一个块需要在某个流式多处理器上执行。假设图中或本应用程序中的第一个块被分配到这个 SM
上执行。但这又引发了一个新问题：因为这个 SM中有四个分区，但我们这里只有一个块。这个被称为“块”的单一软件单元应如何分
配到 SM 内部的四个硬件分区中？

如果我们决定将整个块只分配给其中一个分区，就会导致资源利用率不足，因为我们会有三个空闲的分区。这一考虑引出了软件层级的第
三级——Warp（线程束），以避免浪费可用的硬件资源。

\subsection{Warp与调度}

此处的每个软件块都会被细分为更小的单元，称为 Warp。例如，如果我们决定将此处的第一个块划分为四个 Warp，那么每个
Warp 就可以分配到该 SM 中的一个不同分区。四个 Warp 对应四个分区，在这种情况下，我们可以为每个分区分配一个
Warp。

但让我们考虑另一个例子。如果我们增加 Warp 的数量，比如每个块有 32 个Warp，而我们有四个分区，那么每个分区将
执行八个 Warp。如果你为每个硬件单元分配了更多任务（比如一个分区有八个Warp），那么你就需要一个管理者，你需要在这
里设置一个小的管理者。这就是为什么我们有一个称为 WarpScheduler（Warp 调度器）的单元，在每个分区中都有
一个 Warp 调度器。因为有时我们会为一个分区分配多个Warp，所以我们需要一个这里的组织者或管理者。

如果我放大这张图，就能看到该分区内的 Warp调度器单元。正如我们所说，该单元存在于每个分区中，负责在每个时钟周期中调度
这八个 Warp中的某一个。这是在硬件层面；而在软件层面，一个 Warp 默认通常由 32 个线程组成。

进入第四级，我们看到每个分区包含若干个核心。Warp中的每个线程都会在一个分区内独立的核心上执行。这种设置确保分区中的每
个核心都积极参与计算过程。理解硬件和软件中的这四个层级，对于高效配置你的CUDA 应用程序至关重要。

块的数量以及每个块中的线程数量，正如我们在接下来的文章中将探讨的那样，是启动任何 CUDA应用程序时需要指定的两个关键参
数。关于 Warp，我们可以通过将块大小（即每个块的线程数）除以 32 来计算每个块中的Warp 数量，因为 Warp
的大小是固定的，等于 32 个线程。
